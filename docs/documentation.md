# Документация AeroMission Planner

## 1. Назначение

AeroMission Planner — сервис планирования полетных заданий для группы БВС. Он помогает оператору быстро понять, какие аппараты использовать, как разрезать область съемки на галсы, сколько времени займет выполнение работ и какие KML/GeoJSON-файлы передать в следующую систему планирования или оператору.

Решение соответствует требованиям кейса: работает в браузере на ПК, принимает произвольные точки старта, парк БВС, область съемки, тип съемки, разрешенное воздушное пространство, бесполетные зоны и резервные посадочные площадки. Выход — индивидуальные маршруты для каждого БВС.

## 2. Архитектура

Система состоит из трех слоев.

1. **Web UI** — статический интерфейс без обязательной сборки. Позволяет редактировать сценарий, выбирать критерий оптимизации, запускать расчет, визуализировать маршруты и скачивать GeoJSON/KML.
2. **FastAPI backend** — REST API, валидация входных данных, запуск планировщика, экспорт миссий.
3. **Planning core** — геометрическая обработка полигона, построение галсов, обход ограничений, распределение работ между БВС.

Поток данных:

```text
JSON-сценарий -> Pydantic validation -> локальная проекция координат -> рабочая зона
-> вычитание no-fly зон -> генерация галсов -> распределение галсов по БВС
-> safe path routing -> миссии БВС -> GeoJSON/KML
```

## 3. Входные данные

Сценарий описывается JSON-объектом:

- `launch_points` — координаты взлетно-посадочных пунктов;
- `reserve_points` — резервные точки посадки;
- `fleet` — доступные БВС, количество, скорость, автономность, максимальная высота, полезные нагрузки;
- `survey_area` — область съемки;
- `allowed_airspace` — граница разрешенного воздушного пространства;
- `no_fly_zones` — бесполетные зоны;
- `survey_type` — RGB, multispectral, IR, LiDAR, geophysical;
- `wind_speed_mps` и `wind_direction_deg` — параметры ветра;
- `optimization` — `min_time`, `min_airtime`, `balanced`;
- `max_work_time_min`, `max_drones` — ограничения пользователя.

## 4. Алгоритм оптимизации

### 4.1 Подготовка геометрии

Координаты переводятся в локальную метрическую систему относительно центра сценария. Это позволяет считать длины маршрутов, расстояния и площадь без сложной GIS-инфраструктуры.

Рабочая зона считается так:

```text
work_area = survey_area ∩ allowed_airspace - no_fly_zones
```

Если после вычитания ограничений зона пустая, сервис возвращает предупреждение.

### 4.2 Генерация галсов

Для каждого типа съемки задана инженерная ширина полосы покрытия и базовая высота:

| Тип съемки | Высота, м | Ширина полосы, м |
|---|---:|---:|
| RGB | 120 | 95 |
| Multispectral | 110 | 75 |
| IR | 100 | 85 |
| LiDAR | 80 | 55 |
| Geophysical | 70 | 45 |

Планировщик строит lawnmower-полосы в двух направлениях и выбирает вариант с меньшим числом полос и меньшей общей длиной. Это снижает число разворотов и суммарный налет.

### 4.3 Распределение между БВС

Парк БВС разворачивается в конкретные единицы. Для каждой единицы учитываются:

- крейсерская скорость;
- автономность;
- безопасный резерв батареи 15%;
- точка старта;
- ближайшая резервная посадка;
- поправка на ветер.

Режимы оптимизации:

- **минимум времени** — балансирует загрузку так, чтобы минимизировать момент завершения последнего БВС;
- **минимум налета** — добавляет штраф за активацию нового аппарата и избегает лишнего использования всего парка;
- **баланс** — компромисс между сроком выполнения и ресурсом парка.

Такой подход учитывает ответ экспертов: пользователь может задать ограничение по сроку или числу БВС, а система возвращает выполнимость, требуемое число активных БВС и расчетное время.

### 4.4 Обход бесполетных зон

Для перелетов между галсами используется visibility graph. Вершины графа — старт, финиш и точки расширенных контуров no-fly зон. Ребро добавляется только если оно не пересекает запретную область и находится в разрешенном воздушном пространстве.

## 5. Выходные данные

Для каждого БВС формируется:

- `drone_id`, модель;
- точка старта и посадки;
- список waypoints с высотой, скоростью и действием;
- последовательность этапов полета;
- длина маршрута;
- время полета;
- число назначенных галсов;
- статус `planned` или `capacity_warning`.

Общая сводка содержит:

- выполнимость;
- суммарный налет;
- длительность работ;
- количество активных БВС;
- площадь съемки;
- число галсов;
- предупреждения.

## 6. API

### `GET /api/health`

Проверка работоспособности сервиса.

### `POST /api/plan`

Тело запроса — сценарий миссии. Ответ — `PlanResult` с миссиями БВС.

### `POST /api/export/geojson`

Принимает `PlanResult`, возвращает FeatureCollection с линиями маршрутов и точками.

### `POST /api/export/kml`

Принимает `PlanResult`, возвращает KML-документ.

## 7. Инструкция по запуску

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn backend.app.main:app --host 0.0.0.0 --port 8000
```

Открыть `http://localhost:8000`.

Тесты:

```bash
pytest -q
```

## 8. Ограничения текущего прототипа

- Рельеф и препятствия учитываются через полигональные зоны, без подключения внешних DEM-сервисов.
- Камера абстрагирована типом съемки и шириной полосы; конкретную модель камеры можно расширить через поле `camera` в `DroneSpec`.
- Для больших сценариев стоит заменить greedy assignment на MILP/OR-Tools или evolutionary search.
- Текущий UI использует Canvas-визуализацию без внешних карт, чтобы демо работало без API-ключей и не нарушало лицензии тайлов.

## 9. Почему решение конкурентоспособно

Решение не ограничивается красивой картой: в нем есть полный расчетный контур от геометрии зоны до экспортируемых миссий. Оно учитывает практические вопросы из обсуждения: противоречие между временем и налетом, выбор числа БВС пользователем, 150 м высоты, no-fly зоны, резервные посадки и отсутствие обязательного внешнего картографического API.
